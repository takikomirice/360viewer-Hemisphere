# ホットスポット表示・ジャンプの先読み検証

2026-09-11、実際のテスト用 `/dev` に登録された写真・音楽・シーンジャンプで検証。基準コミットは `59e47f9`。データの追加・変更・削除、共有権限の変更は行っていない。

## 採用した変更

- 現在のホットスポットのジャンプ先を最大4シーン、既存のメタデータ先読みキューの先頭へ入れる。進行中の通信を重複させず、サムネイル切替と同じマーカー・方位情報のキャッシュを使う。通常の一覧20件の準備も続く。
- ジャンプマーカーのホバー・フォーカスで、サムネイルと同じ画像・情報の先読み処理を使う。既存の直リンク／Base64／fallbackの選択を維持する。
- シーン表示が完了してから500ms間隔の処理で、通常の写真・音声添付を合計最大2件、1件ずつ先読みする。シーンをまたいでも背景添付取得は同時1要求。非表示タブやシーン切替中は新しい取得を止め、編集・通信量節約・2Gでは開始しない。クイズ添付はこの自動先読みの対象外。
- 写真のホバー・フォーカス、先読み、ポップアップが同じ取得要求を共有する。閉じたポップアップは書き換えず、有効な応答は次回のために保持する。写真キャッシュは最大4件、音声は既存の最大2件。音声の自動再生はしない。
- 写真・音声の応答が30秒間来なければ失敗として終了し、再度開いたときに再取得できるようにする。タイムアウト後の古い応答・二重完了は無視する。

## 実測条件

Windows Chrome、同じ回線・同じ添付、`mode=public&perf=1`、配信は既存の `auto`。新しいタブごとにクライアントのアプリキャッシュは空。ブラウザーのHTTP画像キャッシュは維持しており、完全な初回ネットワーク取得の比較ではない。

`hotspotPrefetch=0` と `1` を交互に各2試行。既存の一覧メタデータ先読みは両方で有効。ホームシーンの描画完了から20秒後（実測20,007〜20,032ms）に操作開始。マウスホバーの影響を避けて実際の `onMarkerClick` をブラウザーの計測コンテキストから呼び出した。

写真は画像のデコード完了（completeかつnaturalWidth>0）、音声はreadyState>=2になるまでを20ms間隔で確認。再生開始の計測ではない。添付試行は写真→音声の順。ジャンプは別タブで添付操作をせず、20秒後に直接実行し、既存のsceneStart→pannellumLoadを測定した。

## 制約と解釈

- 取得そのものが速くなったという結果ではなく、閲覧中に取得を済ませて操作後の待ち時間を減らした結果。シーン表示直後の即操作、3件目以降、遅い回線・大きい添付では待ち時間が残る。音声はシーン移動時に既存仕様どおりキャッシュを破棄する。
- 自動先読み分の通信が発生する。写真・音声の権限検証は従来のGAS APIを使い、公開URL化やサーバーAPIの変更はしていない。
- 新規ページの最初のシーン表示は無効2,318〜3,783ms、有効3,713〜6,155msだった。少数試行かつGASの応答変動があるため、初期表示の改善は主張しない。新しい添付先読みは描画完了後に開始する。
- 計測は各条件2回の実機検証であり、端末・回線全般の保証や負荷試験ではない。先読み無効時も、十分長く閲覧すれば従来の一覧先読みでジャンプ先が取得済みになる。
- `hotspotPrefetch=0` は今回の自動添付先読み・ジャンプ優先・写真意図先読みの比較用。既存の音声ホバー先読み、ジャンプ画像先読み、一覧メタデータ先読みは残る。写真要求共有・件数制限・タイムアウトは無効化しない。
