# レスポンシブUI整備 第1段階 テーマ切替追加設計

## 目的と範囲

レスポンシブUI整備 第1段階で対象外としていたライト／ダークテーマ切替を追加する。公開・internalではトップバーを復活させず、写真領域上にフローティングテーマ切替だけを表示する。編集画面では既存トップバー内に同じテーマ状態を操作するボタンを置き、二つの切替が同時表示されないようにする。

既存の上部余白修正、レスポンシブレイアウト変数、Playwrightハーネス、public／internal／editの権限制御、編集トークン、360／2D表示、シーン一覧、ホーム、アップロード、ホットスポット、マーカー移動、Googleサイト埋め込みを維持する。GASの権限、データ構造、サーバーAPIは変更しない。

OSテーマの変更をページ表示中に動的追従する機能は対象外とする。保存テーマがない場合だけ初期表示時の`prefers-color-scheme`を読み、一度ユーザーが切り替えた後は保存値を優先する。

## 検討案

### A. 既存色をすべて意味別CSS変数へ一括置換

長期的な統一性は高いが、今回の範囲に対して差分が大きく、画像表示や既存編集操作へ予期しない影響を与えやすい。第1段階の追加としては回帰リスクが高いため採用しない。

### B. 主要な意味別CSS変数 + 対象を絞ったダーク指定（採用）

背景、前景、境界線、操作面、入力欄、フォーカスリングなど共通性の高い色を意味別CSS変数へまとめる。既存CSSの構造を大きく変えず、トップバー、サイドバー、編集バナー、モーダル、ポップアップ、入力、ボタン、ヒント、トーストなど必要なUIへ変数または対象を絞ったダーク指定を適用する。

画像を描画する要素にはテーマ用フィルターを使わず、既存レイアウトへの影響を限定できるため採用する。

### C. UI全体へ`filter`や`invert`を適用

変更量は小さいが、360／2D画像、アイコン、状態色の見え方を壊し、コントラストを要素ごとに保証できない。画像へフィルターを適用しない要件とも相性が悪いため採用しない。

## テーマ状態と初期描画

テーマ値は`light`と`dark`だけを有効値とする。保存先はブラウザの`localStorage`とし、アプリ専用の固定キーを一つ使用する。

初期テーマは次の順で決定する。

1. `localStorage`の保存値が`light`または`dark`なら、その値を使用する。
2. 保存値がない、または無効なら、初期表示時の`matchMedia('(prefers-color-scheme: dark)')`を使用する。
3. `matchMedia`を利用できない場合は`light`を使用する。

CSSの読み込みより前に`<head>`内の小さな初期化スクリプトでテーマを決定し、`document.documentElement.dataset.theme`へ反映する。これにより、ダークテーマ利用時にライトテーマが一瞬表示される現象を抑える。

ストレージアクセスがブラウザ設定や埋め込み環境で例外になっても、初期化と画面表示は継続する。その場合は保存せず、現在のページ内だけで選択テーマを反映する。無効な保存値は使用しない。

ページ表示中のOSテーマ変更イベントは監視しない。保存値がない状態でも、初期化後のテーマは再読み込みまで固定する。

## 共通テーマ操作

公開用と編集用のボタンは、同じテーマ取得・反映・保存・表示同期処理を使用する。切替時は次を一つの処理で行う。

- 現在値を`light`から`dark`、または`dark`から`light`へ変更する。
- `<html data-theme>`を更新する。
- `localStorage`へ新しい値を保存する。
- 公開用と編集用の両ボタンについて、アイコン、`aria-label`、`title`、押下状態を同期する。

現在がライトならボタンは「ダークテーマに切り替える」、現在がダークなら「ライトテーマに切り替える」という次の操作を示す。JavaScriptから追加するテーマクラスでレイアウトを制御せず、既存の`data-app-mode`とトップバー表示契約を利用する。

## モード別表示

### public／internal

既存トップバーは引き続きレイアウトから完全に除外する。フローティングテーマ切替だけを`#ui-overlay`内へ置き、写真領域上の固定オーバーレイとして表示する。

ボタンは概ね44px四方のタップ領域を持ち、`--app-safe-top`と`--app-safe-right`を参照する。全画面、ホーム、画質、ジャイロの右上操作列と同じ高さに並べる場合は、その列の左隣へ配置して矩形が重ならないようにする。シーン一覧の開閉によって位置を動かさず、レイアウト高を消費しない。

キーボードでフォーカスと押下ができ、`aria-label`、`title`、明瞭な`:focus-visible`を持つ。全画面表示でも利用できる。

### edit

既存トップバーの右側操作群へテーマ切替を追加する。狭い画面では既存の折り返し規則に従い、画面外へはみ出さず、概ね44pxのタップ領域を維持する。

編集トップバーが表示される画面ではフローティング版を非表示にする。公開用と編集用の表示条件は相互排他的とし、可視なテーマ切替が同時に二個にならないことをテストする。

mode指定なしの既存閲覧画面は、従来のトップバー表示契約を維持し、トップバーが表示される場合は編集側のテーマ切替を使用する。

## CSSテーマ契約

ライトテーマを既存表示に近い既定値とし、`html[data-theme="dark"]`で意味別変数を上書きする。最低限、次の役割を変数として扱う。

- ページ背景と主要な面
- 強い面、弱い面、ホバー／アクティブ面
- 主文字、補助文字、無効文字
- 通常境界線と強調境界線
- 入力欄背景と文字
- ボタン背景と文字
- オーバーレイ背景
- フォーカスリング
- 成功、警告、エラーなど既存状態色に必要な背景と文字

テーマ対象は次を含む。

- トップバー
- サイドバーとシーン項目
- 編集バナー
- 各モーダルとダイアログ
- ポップアップとコンテキストメニュー
- 入力欄、選択欄、テキストエリア
- 通常ボタン、アイコンボタン、無効状態
- ヒント、ヘルプ、トースト、アクセス通知
- フローティングテーマ切替
- キーボードフォーカスリング

半透明面は、ライト／ダーク双方で背後の写真に対して文字とアイコンを判読できる不透明度と影を使う。テーマ切替そのものには色だけでなくアイコンとラベルを使用する。

`html`の`color-scheme`もテーマに合わせ、ブラウザ標準フォーム部品とスクロールバーの配色を補助する。

## 画像表示の保護

360パノラマ、2D画像、サムネイル、Pannellumの描画面へテーマ用の`filter`、`opacity`、`mix-blend-mode`を適用しない。テーマ変更はUI面と文字、境界線に限定する。

Playwrightでは360表示領域と2D画像について、ライト／ダーク切替後も利用可能なサイズを保ち、テーマ由来のフィルターが`none`であることを確認する。

## Playwrightハーネスと検証

既存ハーネスは本番の`index.html`、`styles.html`、`app.html`を読み込む構造を維持する。テーマテストのために本番コードへハーネス専用分岐を追加しない。ブラウザの`localStorage`と`page.emulateMedia`を使用して保存値とOS初期値を検証する。

対象画面幅は次の5種類とする。

- 1440×900
- 1024×768
- 390×844
- 360×800
- 800×360

public、internal、editについて、360／2D、ライト／ダーク、シーン一覧の開閉を組み合わせて次を検証する。

- public／internalではトップバーが非表示で、フローティングテーマ切替だけが可視である。
- editではトップバー内テーマ切替だけが可視である。
- 可視なテーマ切替が同時に二個にならない。
- クリックで`<html data-theme>`が変化する。
- 切替値が`localStorage`へ保存される。
- 再読み込み後も保存テーマが維持される。
- 保存値なしではOS設定を初期値として使用する。
- ライト／ダーク双方で横方向オーバーフローがない。
- シーン一覧開閉後も画像領域上端、テーマ切替、主要操作の位置がずれない。
- フローティングテーマ切替が全画面、ホーム、画質、ジャイロ、シーン一覧と重ならない。
- 390×844、360×800、800×360でテーマ切替と主要UIが画面内にあり、操作可能な大きさを持つ。
- 360／2D画像が利用可能領域を維持し、テーマ用フィルターを受けない。
- ページ操作中に未処理のJavaScriptエラーがない。

位置と重なりは要素矩形、画面内判定、矩形交差で検証し、画像のピクセル完全一致には依存しない。確認用スクリーンショットは既存のGit管理対象外成果物フォルダへ出力できる。

## NodeテストとTDD

実装前にテーマ契約を表すテストを追加し、失敗を確認する。静的・単体テストでは少なくとも次を検証する。

- 初期化スクリプトがCSS読み込み前に存在する。
- 保存値の検証、OSフォールバック、`data-theme`反映がある。
- 共通切替処理が二つのボタンを同期する。
- モード別の相互排他的表示規則がある。
- ボタンにアクセシビリティ属性がある。
- ダークテーマの必須UI面とフォーカス指定がある。
- 画像へテーマ用フィルターを適用しない。

Playwrightテストも先に追加して対象失敗を確認し、その後に最小実装を加える。

## 回帰と完了条件

既存の権限・編集トークン・GAS API・データ構造へ変更がないことを差分で確認する。public／internalの上端0、editの実測トップオフセット、レスポンシブな画像領域とシーン一覧の既存テストを維持する。

完了時に次をすべて成功させる。

- `node --check Code.js`
- `node --test tests/*.test.js`
- `npm run test:browser`
- `git diff --check`

テスト失敗、未処理JavaScriptエラー、主要UIの重なり、横方向オーバーフローが残る場合は完了としない。コミット、push、PR作成、GASデプロイは行わない。
