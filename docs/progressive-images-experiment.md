## 素材と容量

ログイン済みDriveの表示済みプレビューを2枚取得して使用。寸法は両方3306×1653。
7.9～8MB程度の原寸JPEGを使用した実験ではない。
画像はユーザーのDriveから取得したため、原画像・生成物・取得URLは公開Gitに含めない。

| 素材 | 入力JPEG | 1024pxプレビュー | 320×180 WebP | 同サイズJPEG | 全タイル合計 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 試作1 | 988,932 B | 89,676 B | 17,802 B | 19,683 B | 1,112,113 B |
| 試作2 | 946,016 B | 89,366 B | 17,246 B | 19,385 B | 1,046,614 B |

サムネイルは全景を単に縮小せず、yaw/pitch/hfovを指定する透視投影で切り出す。
WebPはこの2枚でJPEGより約9.6～11.0%小さい。同じ品質設定値の比較であり、主観画質が完全に等しいとは限らない。
タイルはcube1024、tile512、2階層、6面。全タイル合計は入力JPEGより大きい。
分割化の目的は、最初から全方向の最高解像度を取得しないことにある。

## 並列取得の実測

Chromeのローカル比較画面で16件を取得。1件ごとにサーバーで120msの人工待ち時間を追加し、キャッシュを使わないURLとした。
同じサムネイルを16回別URLで取得する通信実験であり、16種類の写真の比較ではない。

| 同時取得数 | 最初の1枚 | 全16件 | 失敗 |
| --- | ---: | ---: | ---: |
| 1 | 131ms | 2,133ms | 0 |
| 4 | 131ms | 544ms | 0 |

別の試行では4並列536ms、1並列2,150ms。取得した1枚ずつ画面へ追加できた。
初期表示1枚の時間はほぼ変わらず、一覧が揃う時間が短くなった。
人工的な待ち時間に対する効果であり、GASや実回線で約4倍になるとの保証ではない。
連打して並列上限を超えないよう、実験中は新しいバッチの開始を無効にする。
未開始の取得はキャンセルでき、単独の失敗で残りが止まらない。

## Drive配信の実測

Drive画面で観測した、認証済みユーザー向け画像URLをローカル画面から試した。

- 通常のimg表示: 成功、922ms、3306×1653。
- 同じURLにcrossOrigin=anonymousを指定: 失敗、332ms。

この結果は、ログイン済みChromeでの成功であり、ログインしていない公開閲覧者への配信を保証しない。
同じ画像でもサムネイル用imgとWebGLパノラマで取得条件が違う。
短命なDriveプレビューURLを恒久的な公開配信URLとして保存しない。
公開タイルには認証・CORS・キャッシュを満たす配信経路の実証が必要で、配信先の選定は未完了。

## パノラマ描画の観測と限界

実際のPannellum 2.5.7で全景・全体縮小・分割の3方式を表示した。
公開アプリは2.5.6なので、これをv2.1.1対現行の同条件比較とは扱わない。
ローカル試作の左メニュー幅もキーボードで変更できた。

キャッシュ回避、同じ素材・画角の1回の観測:

| 方式 | renderer-ready | current-view-settled | 完了済み画像取得数 | 観測転送量 |
| --- | ---: | ---: | ---: | ---: |
| 全体JPEG | 219ms | 235ms | 1 | 946,316 B |
| 分割 | 33ms | 3,416ms | 16 | 654,972 B |
| 全体縮小 | 2,013ms | 3,014ms | 1 | 89,666 B |

`renderer-ready` は初期化だけ。分割時は画像到着より先に発生する。
`current-view-settled` は現在の可視タイルが読み込み中でなくなり、2フレーム経過した時点。全方向の完了や実際の最初のピクセル描画時刻ではない。
画像取得数・転送量は対象シーンの対象パスに絞った完了済みResourceTiming記録で、タイル自体の完全性を保証する指標ではない。
全体縮小でも描画待ちが長く、フレーム間隔・実行環境の影響を分離できていない。この少数の値から速さの優劣を確定しない。
Pannellum側は応答性を保つため、タイルの開始処理を1フレームに1件としている。ブラウザのフレーム進行にも影響される。
分割すれば常に速い、あるいは本番が高速化済み、とは結論しない。

追加の2画像間切替ではcurrent-view-settledが250ms、247msとなった。
同じURLへの再訪では画像2が271ms、ResourceTimingの観測転送量0 Bとなり、ブラウザキャッシュの再利用を確認できた。
このばらつきも含め、中央値や遅いケースの基準に使える回数・条件の比較は今後必要。

## 再実行

```powershell
npm ci
npm run images:generate -- <正距円筒画像.jpg> output/quality-audit/progressive-images
npm run preview:images
```

http://127.0.0.1:4174 を開く。ポートはPROGRESSIVE_PORTで変更できる。
試作サーバーは127.0.0.1のみに待受し、指定した生成物ディレクトリと試作ファイルだけを返す。
生成済み画像はGit対象外。GASへのclasp送信対象は既存5ファイルのまま。
