# レスポンシブUI整備 第1段階 設計

## 目的と範囲

公開・internalでは画像領域、シーン一覧、ローディング、遷移オーバーレイを画面上端から開始し、非表示トップバー由来の余白をなくす。編集可能画面では既存機能を残したまま、トップバーと編集バナーの実測高をコンテンツ開始位置として共有し、狭い画面でも操作と画像領域を維持する。

ホットスポット追加画面のボトムシート化、仮マーカー、添付写真アップロード、権限・トークン・GASデータ構造の変更は対象外とする。現行コードにライト／ダーク機能が存在しないことを確認し、ユーザー指示に従ってテーマ切替の新規実装とテストも対象外とする。

## 現状と原因

`styles.html`にはトップバー高60px、編集バナー込み100pxが、サイドバー、展開タブ、ローディング、遷移オーバーレイ、モバイル360/2D領域へ個別に埋め込まれている。公開・internalのトップバーは`google.script.url.getLocation`完了後にインラインスタイルで隠れるため、初回描画時にはトップバーと60pxオフセットが残り得る。公開デスクトップのサイドバーはトップバー非表示後も`top: 60px`のままである。

編集トップバーは固定60pxで折り返さず、幅が狭いと右側コントロールが画面外へ出る。編集バナーも固定40pxなので、文言が折り返す幅では実際の占有高と画像領域の開始位置が一致しない。

## 検討案

### A. CSS固定値をメディアクエリごとに上書き

変更量は小さいが、トップバーが折り返した実高を表現できず、新しいボタン追加時に各ブレークポイントの固定値が再び分散するため採用しない。

### B. 初期モードのサーバー埋め込み + 実測値をCSS変数へ反映（採用）

`doGet`で許可済みモード名だけをテンプレートへ渡し、`body[data-app-mode]`に設定する。公開・internalはJavaScriptコールバック前からトップバーを除外し、`--app-top-offset: 0px`にする。編集可能画面は`ResizeObserver`とresizeイベントでトップバーと表示中バナーの実高を測り、CSS変数を更新する。すべての画像領域と写真領域オーバーレイは同じ変数を参照する。

初回描画、可変高、将来のツールバー項目追加に一つの仕組みで対応でき、本番コードはテストハーネスへ依存しない。

### C. JavaScriptで各要素の`top`と`height`を個別更新

ブラウザ差を吸収できるが、対象要素の追加漏れとインラインスタイル競合を生みやすい。レイアウト規則がCSSとJavaScriptへ分散するため採用しない。

## レイアウト契約

ルートに次の変数を置く。

- `--app-viewport-base`: `100vh`をfallbackにし、対応ブラウザでは`100dvh`
- `--app-toolbar-height`: 表示中トップバーの実測高
- `--app-edit-banner-height`: 表示中編集バナーの実測高
- `--app-top-offset`: モードに応じた写真領域の開始位置
- `--app-viewport-height`: `--app-viewport-base - --app-top-offset`
- `--app-safe-top` / `--app-safe-right` / `--app-safe-bottom` / `--app-safe-left`: `env(safe-area-inset-*)`

公開・internalと写真全画面状態では`--app-top-offset: 0px`とする。通常の編集可能画面はトップバー実高、編集操作中はトップバー実高と編集バナー実高の合計とする。

360、2D、シーン一覧、ローディング、遷移オーバーレイ、サイドバー展開タブ、画像右上の操作群はこの契約を参照する。モーダルの背景は操作を確実に遮断するため引き続き全ウィンドウを覆うが、サイズ計算は`100dvh`へ移行する。

## モード別上部UI

- `public`: トップバー、編集ボタン、編集状態、アクセス通知を表示しない。画像と写真領域オーバーレイは上端0から始める。
- `internal`: `public`と同じ上部レイアウトとする。
- `edit`かつ有効トークン: 既存トップバーを表示する。編集モードON時は既存編集バナーも表示し、両方の実高を写真領域から差し引く。
- modeなしの閲覧専用: 既存アクセス通知とトップバーの挙動を維持する。

## 狭い編集画面

トップバーは折り返し可能にし、狭い幅ではタイトル行と操作行に分ける。ラベルを隠すボタンには`aria-label`と`title`を残し、ボタン、シーン項目、開閉操作は概ね44px以上のタップ領域を持つ。hover色に加え`:focus-visible`と`:active`を用意する。360/2D領域は実測トップUIとモバイルシーン一覧を除いた残りを埋める。

800×360では幅があるためトップバーを原則一段に保ち、画像領域の高さを確保する。390×844と360×800では折り返しを許可し、下部シーン一覧を操作できる状態を維持する。

## ブラウザ確認ハーネス

GASテンプレートはそのまま静的配信できないため、Nodeのローカルサーバーで`index.html`へ`styles.html`と`app.html`を同じ順序で埋め込む。`google.script.url.getLocation`、`google.script.run`、Pannellum、画像応答だけを決定的なfixtureで置き換える。本番ファイルはハーネスを参照しない。

Playwrightは実Chromiumで公開、internal、編集、360、2D、シーン一覧開閉を操作する。位置・サイズ・可視性・横方向scrollWidthを主な判定にし、画像のピクセル一致は要求しない。修正前後の代表スクリーンショットは`output/playwright/`へ保存し、同フォルダをGit管理対象外にする。

## 回帰と完了条件

既存Node 240テスト、追加静的テスト、Playwrightテスト、`node --check Code.js`、`git diff --check`がすべて成功すること。公開・internalの写真領域上端とオーバーレイ上端は0付近、編集画面ではトップバーが表示され、その下から写真領域が始まること。指定5幅で水平オーバーフロー、主要操作の画面外配置、シーン一覧開閉後の位置ずれがないことを座標で確認する。
